# PROJECT: PROFESSIONAL 2D FANTASY TOWER DEFENSE GAME

Act as a Senior Game Developer, Game Engine Architect, TypeScript Engineer, Performance Optimization Specialist, and UI/UX Designer.

Your task is to design and develop a complete, production-quality, browser-based Tower Defense Game from scratch.

Do not create just a static UI, prototype, or visual demonstration. Build a fully functional, playable game with real-time gameplay, animations, combat mechanics, progressive difficulty, and a scalable architecture.

Use the following technologies:

- React for UI components, menus, HUD, and controls.
- TypeScript for the entire game architecture.
- Vite for development and production builds.
- PixiJS 8 for GPU-accelerated 2D game rendering.
- HTML5 Canvas/WebGL through PixiJS.
- Web Audio API for sound effects and music.

The game must work without requiring a backend, API keys, or external services.

## 10. CRITICAL PERFORMANCE REQUIREMENTS

Performance and scalability are essential.

The following quantities are minimum stress-test targets, NOT maximum entity limits:

- At least 5,000 simultaneously active enemies.
- At least 100 simultaneously active towers.
- At least 1,000 simultaneously active projectiles.

Never introduce arbitrary hardcoded entity caps.

Use dynamically growing storage, allocation strategies, and memory management so the game can support more entities when hardware permits.

Implement:

### Entity management
- Structure of Arrays (SoA).
- TypedArrays for frequently updated numerical data.
- Object pooling and free-list allocation.
- Dynamic buffer expansion.
- Reuse inactive entity slots.
- Avoid unnecessary object creation.

### Simulation
- One centralized fixed-timestep simulation loop.
- Refresh-rate-independent behavior.
- No individual timers or animation loops per entity.
- Efficient enemy movement.
- Efficient projectile processing.
- Optimized collision detection.
- Spatial hashing or spatial grid for target acquisition.
- Avoid unnecessary repeated distance calculations.

### Rendering
- PixiJS sprite batching.
- Texture atlases.
- Viewport culling.
- Sprite reuse.
- Particle pooling.
- Cached static terrain.
- Level of detail where useful.
- Avoid rendering invisible entities.

Do not incorrectly remove active offscreen entities from gameplay simulation just because they are not visible.

### Performance targets
On a declared reference desktop/browser configuration, aim for:
- At least 45 FPS for 95% of frames during the specified stress test.
- Fewer than 5% of frames exceeding 33ms.
- Stable memory during a complete 50-wave campaign.
- Responsive mouse and keyboard interaction.
- No progressive performance degradation caused by memory leaks.

Create a benchmark mode that can generate the required simultaneous stress load.

Measure actual performance. Do not claim that a target has been achieved without running the relevant benchmark.

## 11. GAME LOOP AND TIME MANAGEMENT

Implement a centralized game loop using requestAnimationFrame for rendering and a fixed simulation timestep, approximately 1/60 second.

Use an accumulator and interpolation where appropriate.

Support:
- Pause and resume.
- 1x, 2x, and 3x simulation speed.
- Controlled catch-up steps after frame delays.
- Refresh-rate-independent simulation.
- Separate simulation and rendering responsibilities.

Pausing must freeze gameplay simulation while allowing necessary interface updates.

- No required external APIs.

- Optional PWA/service worker caching.

Do not make gameplay depend on a third-party service.
